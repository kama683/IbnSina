**Статус:** черновик. Вы попросили сформулировать его самостоятельно по
плану (`IBNSINA_DEVELOPMENT_PLAN (1).md`, §4 «Этап 3 — Склад препаратов»),
а не диктовать бизнес-логику в чат заново — этот документ раскрывает 9
пунктов плана в модель данных, права и явные открытые вопросы. Как и на
предыдущих этапах, реализация начинается только после того, как вы
проверите/поправите модель и ответите на вопросы §3.

Код-археология не нужна — это чистый greenfield: в репозитории сейчас нет
`Medication`/`StockBatch`/`StockMovement` вообще, есть только
`Prescription` (`appointment_id`, `medication` — свободный текст,
`dosage`, `frequency`) — бумажный рецепт без всякой связи со складом (см.
открытый вопрос 4).

## 1. Модель данных (предложение)

Деньги — тиыны, `BigInteger`, как во всём проекте. Общий паттерн:
`created_by_id`/`created_at` на каждой мутирующей записи,
`record_audit()` на каждую складскую операцию (приём, списание,
инвентаризация, брак).

### `Medication` (номенклатура)
```
id, code (str, unique), name (str), unit (str — "уп.", "мл", "амп." —
см. открытый вопрос 3), billable (bool, default false — см. открытый
вопрос 6), min_stock_level (int, nullable — порог «мало», открытый
вопрос 8), is_active (bool, default true)
```
Не удаляется — только `is_active=false` (тот же паттерн, что `Service` в
Этапе 2).

### `StockReceipt` (приход)
```
id, supplier (str — см. открытый вопрос 2), invoice_number (str,
nullable — номер накладной поставщика, не путать с Invoice клиники),
received_at (date), created_by_id (FK Employee), created_at, total_cost
(BigInteger, = Σ StockBatch.purchase_price*quantity в этом приходе)
```

### `StockBatch` (партия)
```
id, medication_id (FK), receipt_id (FK StockReceipt), batch_number (str),
expires_at (date), quantity_received (int), purchase_price (BigInteger,
тиыны за единицу)
```
Текущий остаток партии — **не колонка**, а сумма `StockMovement` по этой
партии (инвариант «остаток — производная от регистра движений»).

### `StockMovement` (регистр движений — единственный источник остатков)
```
id, batch_id (FK StockBatch), quantity (int, отрицательное = списание,
положительное = приход/корректировка вверх), movement_type (enum:
receipt|dispense|write_off_defect|write_off_expired|inventory_adjust),
patient_id (FK Patient, nullable — заполнено только у dispense),
appointment_id (FK Appointment, nullable), reason (str, nullable —
обязательно для write_off_*/inventory_adjust), created_by_id (FK
Employee), created_at, approved_by_id (FK Employee, nullable — см.
открытый вопрос 7)
```
Списание (`dispense`) проверяется внутри транзакции с блокировкой строки
партии (`SELECT ... FOR UPDATE`, как требует сквозной инвариант плана) —
нельзя списать больше остатка партии и нельзя списать из партии с
`expires_at < сегодня`.

### Инвентаризация
Отдельной таблицы не предлагаю — `inventory_adjust` это просто ещё один
`movement_type` в `StockMovement` (с обязательным `reason` и, по решению
вопроса 7, возможно `approved_by_id`). Если нужен рабочий процесс
«черновик расхождения → утверждение» (а не мгновенная запись), это меняет
модель — см. вопрос 7.

## 2. Роли и права (проект, требует подтверждения §3)

В плане роли для склада явно не расписаны («приход у ресепшена» — это

| Действие | Предлагаемые роли | Комментарий |

## 3. Открытые вопросы

Формулировки плана по складу гораздо более сжатые, чем по кассе (9 строк
против полноценного раздела в Этапе 2) — большинство архитектурных
развилок план оставляет неявными. Прошу явно решить каждый пункт, а не
позволить мне угадать — цена ошибки здесь высокая (склад пересекается со
схемой Invoice из Этапа 2, переделка задним числом будет дороже).

### Критичные — блокируют модель данных

1. **`Expense` ещё не существует (это модель Этапа 4).** План говорит
   «приход… автосоздание `Expense`» — но бухгалтерия начнётся только в
   Этапе 4. Варианты: (а) в Этапе 3 `StockReceipt.total_cost` просто
   считается и хранится, без реального `Expense` — Этап 4 задним числом
   пройдётся по `StockReceipt` и создаст `Expense` для каждого; (б) уже
   сейчас завести минимальный скелет `Expense` (id, category, amount,
   source_type, source_id, created_at) специально ради этой связки, и
   Этап 4 достроит вокруг него отчётность. (а) проще и не трогает будущий
   Этап 4 дважды; (б) точнее следует тексту плана «автосоздание». Что
   выбираем?

2. **Пересечение со схемой `Invoice`/`InvoiceItem` (Этап 2).** Решение 1
   Этапа 2 сделало `InvoiceItem.service_id` `NOT NULL` — «только услуги»
   — именно потому, что препараты были ещё не спроектированы. План Этапа
   3 (п.5) требует «предложение добавить позицию в счёт» для billable
   препаратов. Как технически добавить строку счёта за препарат: (а)
   снять `NOT NULL` с `service_id` и добавить параллельное nullable
   `InvoiceItem.medication_id` с проверкой «заполнено ровно одно из
   двух» (миграция трогает Этап-2-таблицу); (б) при создании
   `Medication(billable=true)` автоматически заводить связанную
   `Service`-запись 1:1 (тот же `service_id`, без новой колонки в
   `InvoiceItem`, но препарат живёт «под двумя именами» в двух таблицах);
   (в) в Этапе 3 списание препарата и выставление счёта остаются
   независимыми действиями — «предложение» это просто подсказка в UI
   («добавьте вручную услугу из прейскуранта на эту сумму»), никакой
   прямой FK-связи нет. Я склоняюсь к (в) как к наименее рискованному для
   уже закрытого Этапа 2, но это меняет то, что значит «billable» на
   практике — подтвердите.

3. **`Prescription` (существует с Этапа 0) vs складское списание.**
   Сейчас `Prescription.medication` — свободная строка на приёме, никак
   не связанная со складом. В Этапе 3 списание препарата пациенту (план,
   п.4) — это (а) то же самое действие, что заполнение `Prescription`,
   только `medication` становится `FK` на `Medication` и заодно создаёт
   `StockMovement`; или (б) полностью отдельное действие/сущность
   (`StockMovement.dispense` сам по себе, `Prescription` остаётся как
   был, просто бумажный список назначений, без связи с фактическим
   складским списанием)? (а) логичнее (что назначено, то и списано), но
   меняет существующую модель `Prescription`.

### Важные — влияют на права и UX

4. **Кто оформляет приход.** Только reception, или head_doctor тоже (как
   почти весь финансовый функционал Этапа 2)? В плане сказано «приход у
   ресепшена» буквально — это исключает head_doctor намеренно, или просто
   не упомянут по умолчанию?

5. **Единицы измерения** — свободная строка на `Medication.unit` (как
   сейчас `Prescription.dosage`), или фиксированный enum (шт./уп./мл/амп.
   и т.п.)? Свободная строка проще, но не даёт валидации количества при
   списании.

6. **FEFO — автоматика или подсказка.** «Списание… по FEFO» — система
   сама выбирает партию с ближайшим сроком годности без участия
   пользователя, или система лишь подсказывает/сортирует партии по сроку,
   а пользователь подтверждает конкретную партию вручную? Автоматика
   надёжнее (не забудут), подсказка — прозрачнее (видно, что списывается).

7. **Кто утверждает списание брака/просрочки и инвентаризацию.** План
   говорит «инвентаризация… с обязательной причиной и утверждением» — кем?
   head_doctor (как подтверждение скидки/возврата в Этапе 2), или
   отдельная роль? И симметричный вопрос: списание брака/просрочки тоже
   требует утверждения, или reception/nurse списывают сразу (причина
   обязательна, но без отдельного шага одобрения)?

8. **Порог «мало» на дашборде** — общий для всей клиники (одно число в
   `.env`, как порог скидки в Этапе 2), или индивидуальный
   `Medication.min_stock_level` на каждый препарат? Второе гибче, но
   требует поля в форме создания/редактирования препарата.

9. **Списание вне приёма.** П.4 плана говорит о списании «из формы
   осмотра» и «из карточки процедур» — оба подразумевают привязку к
   текущему приёму/пациенту в моменте. Бывает ли списание совсем без
   привязки к приёму (например, стационарный пациент получает препарат
   между приёмами, или медсестра расходует материал не на пациента вообще
   — на процедурный кабинет)? Если да, `appointment_id`/`patient_id` в
   `StockMovement` должны быть nullable по-разному, а не парой.

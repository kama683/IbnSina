# IbnSina — План развития системы до многоролевой клинической ERP

**Версия документа:** 1.0
**Статус:** к исполнению
**Базис:** `SYSTEM_OVERVIEW.md` (описание текущей реализации)

---

## 0. Цель и рамки

### 0.1 Что мы строим

Текущая система — **рабочее место одного врача**. Целевая система — **операционная платформа частной клиники**, где работают пять типов сотрудников, ведётся касса, склад препаратов и расчёт зарплат.

### 0.2 Что переиспользуется

Доменное ядро сохраняется почти полностью:

- Пациенты, поиск по ИИН, участки
- Приёмы, статусы, живая очередь
- Форма осмотра, МКБ-10, назначения
- Паспорт здоровья, прививки, аллергии, диспансерный учёт
- Next.js RSC-архитектура, FastAPI + SQLAlchemy + Alembic

### 0.3 Что меняется в основании

- `User ↔ Doctor` (1:1) → `User → Employee → DoctorProfile` (опциональный профиль)
- Отсутствие RBAC → сквозная ролевая модель на бэке и фронте
- Однодокторская запись → многодокторская
- Read-only карточка пациента → редактируемая
- Токен в JS-доступной cookie → httpOnly + refresh

### 0.4 Явно вне рамок (пока)

- Мультифилиальность (закладываем `branch_id`, но UI не делаем)
- Интеграция с ОСМС / страховыми
- Мобильное приложение
- Телемедицина
- Лабораторные интеграции (LIS)

## 1. Принятые решения и дефолты

Ниже — решения по «открытым вопросам». Там, где решение не финальное, указан дефолт и способ его поменять без переписывания схемы.

| # | Вопрос | Принятое решение | Как поменять потом |
|---|---|---|---|
| 1 | Модель зарплаты | Поле `salary_type` на сотруднике: `fixed` \| `percent` \| `fixed_plus_percent`. Дефолт — `fixed`. Процент считается от выручки, атрибутированной этому сотруднику | Добавление нового типа = новое значение enum + ветка в калькуляторе. Схема не меняется |
| 2 | Препараты платные отдельно? | Да, но опционально. У `Medication` есть флаг `billable` и `sale_price`. Списание с `billable=true` предлагает добавить позицию в счёт; с `false` — только расход склада | Флаг на номенклатуре, меняется в UI |
| 3 | Учёт партиями | Да. Партии + сроки годности обязательны | — |
| 4 | Кассовая смена | Да, реализуем. Без неё нет сверки налички | Можно отключить настройкой клиники |
| 5 | Скидки и возвраты | Ресепшен выставляет скидку до порога (`max_discount_percent`, дефолт 10%); выше порога и любой возврат — требует подтверждения главврача | Порог — настройка |
| 6 | Филиалы | `branch_id` (nullable) на ключевых таблицах, единственный филиал по умолчанию, UI не делаем | Включение = добавление селектора филиала |
| 7 | Тип клиники | **Частная**, прямые платежи от пациента. Поле `payer_type` на счёте (`self_pay` \| `insurance` \| `osms`) заложено, но UI только для `self_pay` | Добавление ветки в биллинг |
| 8 | Валюта | KZT, целые тиыны в БД (`BIGINT`), форматирование на фронте | — |

> **Важно:** все денежные суммы хранятся в **минимальных единицах целым числом** (`BIGINT`, тиыны). Никаких `FLOAT`/`DOUBLE` для денег.

### 2.3 Принцип разделения полномочий

**Бухгалтер считает — главврач утверждает.** Бухгалтер не может утвердить и выплатить зарплату, в том числе себе. Аналогично: ресепшен принимает деньги, но возврат подтверждает главврач.

## 3. Целевая модель данных

### 3.1 Блок «Персонал и доступ»

#### `Employee` (новая)
Единая сущность сотрудника. Заменяет роль «Doctor как сотрудник».

| Поле | Тип | Комментарий |
|---|---|---|
| `id` | PK | |
| `full_name` | str | |
| `short_name` | str | генерируется бэкендом (правило уже есть в коде) |
| `initials` | str | |
| `role` | enum | `reception` \| `doctor` \| `nurse` \| `accountant` \| `head_doctor` \| `admin` |
| `position_title` | str | «Врач-эндокринолог», «Старшая медсестра» — для отображения |
| `phone`, `email` | str | |
| `hired_at` | date | |
| `fired_at` | date? | null = работает |
| `status` | enum | `active` \| `on_leave` \| `fired` |
| `salary_type` | enum | `fixed` \| `percent` \| `fixed_plus_percent` |
| `base_salary` | bigint | тиыны, за месяц |
| `revenue_percent` | numeric(5,2) | % от атрибутированной выручки |
| `branch_id` | FK? | задел на филиалы |

> **Увольнение = `status = fired` + `fired_at`.** Физическое удаление сотрудника запрещено — рушится история приёмов, счетов и платежей.

#### `DoctorProfile` (из текущей `Doctor`)
1:1 к `Employee`, только для `doctor` и `head_doctor`.

Поля: `specialty`, `qualification_category`, `area`, `office`, `workplace`, `license_number`, `license_valid_until`, `certificate_number`, `certificate_valid_until`, `about`, `experience_years`.

`Schedule` и `DoctorEducation` переезжают на `employee_id` (график нужен и медсёстрам, и ресепшену).

#### `User` (изменяется)
- `doctor_id` → `employee_id`
- Добавить: `must_change_password` (bool), `last_login_at`, `is_active`
- Роль читается из `Employee.role`, а не дублируется в `User` (единый источник истины)

#### `RefreshToken` (новая)
`id`, `user_id`, `token_hash`, `expires_at`, `revoked_at`, `user_agent`, `ip`.

#### `AuditLog` (новая)
`id`, `actor_user_id`, `entity_type`, `entity_id`, `action` (`create`/`update`/`delete`/`approve`/`login`), `changes` (JSONB: before/after), `ip`, `created_at`.

Обязателен для: всех операций с деньгами, движений склада, изменений мед. данных, кадровых действий.

### 3.2 Блок «Финансы»

#### `Service` (новая) — прейскурант
`id`, `code`, `name`, `category`, `price` (bigint), `duration_minutes`, `is_active`, `revenue_attribution` (enum: `performer` \| `clinic`).

#### `Invoice` (новая) — счёт
| Поле | Комментарий |
|---|---|
| `id`, `number` | человекочитаемый номер, уникальный |
| `patient_id` | |
| `appointment_id` | nullable — счёт может быть без приёма |
| `created_by_id` | сотрудник |
| `status` | `draft` \| `unpaid` \| `partial` \| `paid` \| `refunded` \| `cancelled` |
| `payer_type` | `self_pay` \| `insurance` \| `osms` |
| `subtotal`, `discount_amount`, `total` | bigint |
| `paid_amount` | bigint, денормализация от `Payment` |
| `issued_at`, `cancelled_at`, `cancel_reason` | |

#### `InvoiceItem` (новая) — позиция счёта
`id`, `invoice_id`, `item_type` (`service` \| `medication`), `service_id?`, `medication_id?`, `name_snapshot`, `unit_price_snapshot`, `quantity`, `discount_percent`, `line_total`, `performer_employee_id`.

> **Критично:** `name_snapshot` и `unit_price_snapshot` — копии на момент выставления. Ссылка на текущую цену `Service` недопустима: изменение прейскуранта не должно переписывать прошлые счета.

#### `Payment` (новая) — оплата
`id`, `invoice_id`, `amount` (bigint, **отрицательная для возврата**), `method` (`cash` \| `card` \| `transfer`), `cashier_employee_id`, `cash_shift_id?`, `paid_at`, `is_refund`, `refund_of_payment_id?`, `approved_by_id?`, `note`.

> **Инвариант: платежи append-only.** Никакого `UPDATE` и `DELETE`. Ошибка исправляется сторно-записью (`is_refund = true`, ссылка на исходный платёж).

#### `CashShift` (новая) — кассовая смена
`id`, `cashier_employee_id`, `opened_at`, `closed_at`, `opening_balance`, `expected_cash`, `actual_cash`, `discrepancy`, `status` (`open` \| `closed`), `note`.

Правило: приём наличных возможен только при открытой смене у текущего кассира.

#### `Expense` (новая) — расход клиники
`id`, `category` (`medication_purchase` \| `rent` \| `utilities` \| `salary` \| `equipment` \| `other`), `amount`, `spent_at`, `description`, `created_by_id`, `related_payroll_id?`, `related_stock_receipt_id?`, `attachment_url?`.

#### `Payroll` (новая) — расчёт зарплаты
`id`, `employee_id`, `period_start`, `period_end`, `base_amount`, `attributed_revenue`, `percent_amount`, `bonus`, `deduction`, `total`, `status` (`calculated` \| `approved` \| `paid` \| `cancelled`), `calculated_by_id`, `approved_by_id`, `paid_at`.

Уникальность: один активный расчёт на пару (сотрудник, период).

### 3.3 Блок «Склад препаратов»

#### `Medication` (новая) — номенклатура
`id`, `name`, `international_name`, `form` (таблетки/ампулы/мазь/...), `unit` (шт/мл/уп), `min_stock_level`, `billable` (bool), `sale_price` (bigint), `is_active`.

#### `StockBatch` (новая) — партия
`id`, `medication_id`, `batch_number`, `expiry_date`, `purchase_price_per_unit`, `supplier`, `quantity_received`, `received_at`, `received_by_id`, `stock_receipt_id`.

#### `StockReceipt` (новая) — документ прихода
`id`, `supplier`, `document_number`, `received_at`, `received_by_id`, `total_amount`, `note`. Группирует партии одной поставки и порождает `Expense` категории `medication_purchase`.

#### `StockMovement` (новая) — регистр движений
`id`, `batch_id`, `movement_type` (`receipt` \| `dispense` \| `write_off` \| `return` \| `inventory_adjust`), `quantity` (положительное = приход, отрицательное = расход), `patient_id?`, `appointment_id?`, `invoice_item_id?`, `performed_by_id`, `reason`, `approved_by_id?`, `created_at`.

> **Инвариант: остаток — это `SUM(quantity)` по движениям партии.** Отдельного изменяемого поля «остаток» нет. Если нужна скорость — материализованное представление или кэш, но источник истины — регистр. Так расхождение «в базе 10, на полке 7» становится невозможным на уровне схемы.

**Правила списания:**
- FEFO — первой списывается партия с ближайшим сроком годности
- Списание из просроченной партии запрещено
- Списание в минус запрещено (проверка в транзакции с блокировкой)
- Списание всегда привязано к пациенту и приёму (кроме `write_off` и `inventory_adjust`)

**Алерты:** остаток ниже `min_stock_level`; партия истекает в ближайшие 30 дней; партия просрочена и не списана.

### 3.4 Разделение назначений и выдачи

Сейчас в системе одна сущность `Prescription`. В целевой модели их две, и это принципиально:

| | `Prescription` (существующая) | `StockMovement type=dispense` (новая) |
|---|---|---|
| Смысл | Врач **назначил** препарат | Препарат **физически выдан** в клинике |
| Где покупает пациент | В аптеке сам | В клинике |
| Влияет на склад | Нет | Да, списывает партию |
| Влияет на счёт | Нет | Да, если `billable = true` |
| Кто создаёт | Врач в форме осмотра | Врач или медсестра |

Смешивать их нельзя — иначе назначение витаминов «на месяц» спишет со склада 30 упаковок.

## 4. Этапы разработки

Порядок не переставлять. Каждый этап заканчивается рабочим состоянием системы.

---

### Этап 0 — Фундамент (блокирующий)

**Без этого этапа любой следующий придётся переписывать.**

**Задачи:**
1. Миграция `Doctor` → `Employee` + `DoctorProfile`. Перенос существующих врачей без потери данных.
2. `UserRole` расширен до шести значений; роль — на `Employee`, `User.role` удаляется.
3. FastAPI-зависимости: `get_current_employee()`, `require_roles(*roles)`, `require_self_or_roles()`. Подключение к каждому роутеру вместо общего `get_current_user`.
4. Фронт: контекст текущего сотрудника, роле-зависимый сайдбар, гварды в `proxy.ts` по префиксам маршрутов, компонент `<RoleGate>`.
5. Безопасность: httpOnly cookie для access-токена, `RefreshToken` + ротация, эндпоинт `/auth/refresh`, `/auth/logout`, смена пароля, форс-смена при первом входе.
6. `AuditLog` + middleware/декоратор для автоматической записи.
7. Обновление `seed.py`: по одному сотруднику каждой роли.

**Готово, когда:** ресепшен, залогинившись, физически не может открыть `/finance/payroll` — ни через UI, ни прямым запросом к API.

---

### Этап 1 — Рабочее место ресепшена

**Задачи:**
1. `PATCH /patients/{id}` + UI редактирования карточки (демография отдельно от мед. данных — разные права).
2. Поиск пациента по ИИН с моментальным решением: найден → открыть, не найден → форма создания с предзаполненным ИИН.
3. Многодокторская запись: `doctor_id` в теле `POST /appointments`, выбор врача в форме.
4. Слоты из графика врача, а не из захардкоженного `08:00–13:00`. Учёт `duration_minutes` услуги.
5. Автокомплит пациента в форме записи вместо `<select>`.
6. Отмена и перенос записи с причиной.
7. Общая очередь по всем врачам для ресепшена (текущая `/queue` остаётся персональной для врача).

**Готово, когда:** ресепшен заводит нового пациента и записывает его к любому врачу на свободный слот, ни разу не заходя в БД.

---

### Этап 2 — Касса

**Задачи:**
1. Справочник `Service` + CRUD прейскуранта (редактирует главврач).
2. `Invoice` + `InvoiceItem`: выставление счёта из карточки приёма или отдельно.
3. `Payment`: приём оплаты, частичная оплата, несколько способов на один счёт.
4. Возврат через сторно + подтверждение главврача.
5. Скидки с порогом.
6. `CashShift`: открытие/закрытие смены, сверка налички, расхождение.
7. Печатная квитанция (HTML → печать браузером, PDF позже).
8. Отчёт по смене и за день: выручка, нал/безнал, число чеков.

**Готово, когда:** дневная выручка в отчёте сходится с суммой платежей, и закрытие смены показывает расхождение по наличным.

---

### Этап 3 — Склад препаратов

**Задачи:**
1. Номенклатура `Medication` + CRUD.
2. `StockReceipt` + `StockBatch`: приход у ресепшена, автосоздание `Expense`.
3. `StockMovement` как единственный источник остатков; вьюха/сервис расчёта текущих остатков.
4. Списание на пациента прямо из формы осмотра (врач) и из карточки процедур (медсестра), FEFO.
5. Связка `billable` препарата → предложение добавить позицию в счёт.
6. Инвентаризация: фактический пересчёт → `inventory_adjust` с обязательной причиной и утверждением.
7. Списание брака и просрочки.
8. Дашборд склада: остатки, «мало», «истекает», «просрочено».
9. История: по препарату (все движения) и по пациенту (что получал).

**Готово, когда:** нельзя списать больше, чем есть; нельзя списать из просроченной партии; сумма движений всегда равна фактическому остатку.

---

### Этап 4 — Бухгалтерия

**Задачи:**
1. `Expense`: ввод и категории, привязка к поставкам препаратов автоматически.
2. Атрибуция выручки: каждая `InvoiceItem` знает исполнителя → база для процента.
3. Калькулятор `Payroll` по трём моделям оплаты.
4. Утверждение и выплата зарплаты главврачом → автосоздание `Expense` категории `salary`.
5. Отчёты:
   - P&L за период (доходы − расходы)
   - Выручка по врачам
   - Выручка по услугам и категориям
   - Структура оплат (нал / карта / перевод)
   - Дебиторка — неоплаченные и частично оплаченные счета
   - Расходы по категориям
6. Экспорт отчётов в XLSX.

**Готово, когда:** бухгалтер закрывает месяц, не открывая ни одной таблицы вручную.

---

### Этап 5 — Панель главврача

**Задачи:**
1. Список сотрудников с фильтрами по роли и статусу.
2. Найм: создание `Employee` + `User` + временный пароль с форс-сменой.
3. Увольнение: деактивация, а не удаление; блокировка входа; сохранение истории.
4. Редактирование условий оплаты сотрудника.
5. Очередь утверждений: возвраты, скидки выше порога, инвентаризация, зарплаты.
6. KPI по врачам: приёмы, завершённые, средняя длительность, выручка, повторные пациенты.
7. Сводный дашборд: финансы + склад + загрузка врачей на одном экране.
8. Просмотр журнала аудита с фильтрами.

**Готово, когда:** главврач нанимает сотрудника, выдаёт доступ и выплачивает ему зарплату полностью через интерфейс.

---

### Этап 6 — Долги и полировка

1. **Тесты.** Обязательный минимум — pytest на: расчёт итога счёта, частичную оплату, возврат, FEFO-списание, запрет ухода в минус, калькулятор зарплаты, матрицу прав. Это места с максимальной ценой ошибки.
2. `AppointmentDiagnosis` — множественные диагнозы.
3. Разделение `Vaccination.dose`.
4. Машина состояний приёма на бэке (запрет отката статуса).
5. Настройки клиники: длительность приёма по умолчанию (сейчас 18 минут в коде), порог скидки, рабочие часы.
6. Уведомления: истекающие партии, неоплаченные счета, низкие остатки.
7. Реальный раздел настроек вместо заглушки.

## 5. Сквозные инварианты

Эти правила действуют во всех этапах и проверяются на уровне БД и сервисов, а не только в UI.

1. **Деньги — целые числа.** `BIGINT` в тиынах. Никаких float.
2. **Платежи append-only.** Исправление — только сторно.
3. **Остаток склада — производная от регистра движений.** Не хранимое изменяемое поле.
4. **Списание в минус невозможно.** Проверка внутри транзакции с `SELECT ... FOR UPDATE`.
5. **Цены и наименования замораживаются в позиции счёта.**
6. **Сотрудники и пациенты не удаляются.** Только деактивация / архивирование.
7. **Каждая финансовая, складская и кадровая операция пишется в `AuditLog`.**
8. **Разделение полномочий:** кто считает — не утверждает.
9. **Проверка прав на бэке обязательна.** Скрытие кнопки в UI — не защита.
10. **Все мутирующие операции — в транзакции.** Счёт + позиции + движения склада создаются атомарно.

## 7. Риски

| Риск | Последствие | Митигация |
|---|---|---|
| Миграция `Doctor` → `Employee` на живых данных | Потеря связей приёмов и госпитализаций | Миграция в два шага: добавить `employee_id` рядом, перенести, потом удалить старый столбец. Бэкап до старта |
| Расхождение остатков склада | Недоверие к системе целиком | Остаток только как сумма движений; тесты на конкурентное списание |
| Ошибка в расчёте зарплаты | Прямой финансовый и репутационный ущерб | Статус `calculated` → обязательное утверждение человеком; детализация расчёта в UI |
| Наличие ролей без реальной проверки на бэке | Ложное ощущение защиты | Каждый эндпоинт объявляет требуемые роли явно; тест на матрицу прав |
| Раздувание этапов | Ни один не доводится до конца | Этап не считается закрытым без выполнения его критерия готовности |

## 8. Порядок действий

1. Бэкап БД и создание ветки.
2. **Этап 0** целиком, до зелёного критерия готовности.
3. Далее этапы 1 → 2 → 3 → 4 → 5 строго последовательно.
4. Тесты из этапа 6 на деньги и склад писать **вместе с** этапами 2 и 3, а не откладывать.

**Не начинать с финансов.** Этап 0 не даёт видимого результата, но без разделения `User`/`Employee` и без RBAC касса и склад будут переписаны заново через месяц.

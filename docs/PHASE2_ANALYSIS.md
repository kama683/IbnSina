## 1. Модель данных (предложение)

Все денежные суммы — **тиыны, `BigInteger`, никогда `float`/`Numeric`**
(инвариант из ТЗ). Общий паттерн с Этапом 1: created_by_id/cancelled_*
поля для аудита, `record_audit()` (Этап 0, коммит 8) на каждую денежную
мутацию.

### `Service` (прейскурант)
```
id, code (str, unique), name (str), category (enum: consultation|
procedure|analysis|other), price (BigInteger, тиыны), duration_minutes
(int|null), is_active (bool, default true)
```
Не удаляется — только `is_active=false` (иначе рассыплются старые
`InvoiceItem`, которые физически не ссылаются на `Service` напрямую, но
логически с ним связаны через `service_id`).

### `Invoice` (счёт)
```
id, patient_id (FK), appointment_id (FK, nullable — счёт может быть без
приёма), status (enum: draft|unpaid|partial|paid|refunded|cancelled),
subtotal (BigInteger, сумма строк до общей скидки), discount_total
(BigInteger, default 0), total (BigInteger, = subtotal - discount_total,
пересчитывается сервером), created_by_id (FK Employee), created_at,
cancelled_at/cancelled_by_id/cancellation_reason (nullable, тот же паттерн,
что Appointment в Этапе 1)
```

### `InvoiceItem` (позиция счёта)
```
id, invoice_id (FK), service_id (FK, nullable — см. открытый вопрос 1),
name_snapshot (str — заморожено на момент выставления), price_snapshot
(BigInteger — заморожено), quantity (int, default 1), discount_amount
(BigInteger, default 0, скидка на строку), line_total (BigInteger,
= price_snapshot*quantity - discount_amount), performer_employee_id
(FK Employee, nullable — задел под Этап 4, UI пока не показывает)
```

### `Payment` (оплата/возврат)
```
id, invoice_id (FK), amount (BigInteger, отрицательная = возврат),
method (enum: cash|card|transfer), cash_shift_id (FK CashShift,
nullable — обязателен, если method=cash), created_by_id (FK Employee),
created_at, reversal_of_payment_id (FK Payment, nullable — заполнено
только у возвратных записей), refund_reason (str, nullable),
approved_by_id (FK Employee, nullable — кто из head_doctor подтвердил
возврат)
```
**Append-only на уровне API**: эндпоинта `PATCH`/`DELETE` для `Payment` не
существует в принципе — это не "не даём по правам", а физическое отсутствие
маршрута. Исправление — только новая запись с `reversal_of_payment_id`.

### `CashShift` (кассовая смена)
```
id, cashier_employee_id (FK Employee), opened_at, opening_balance
(BigInteger), closed_at (nullable), actual_cash (BigInteger, nullable —
заполняется при закрытии), status (enum: open|closed)
```
`expected_cash` и `discrepancy` — не колонки, а вычисляемые в сериализаторе
поля (`opening_balance + Σcash-платежей - Σcash-возвратов` на момент
запроса/закрытия) — так они не могут разойтись с фактическими `Payment`.

## 4. Решения (получены 2026-08-08)

1. Только услуги. `InvoiceItem.service_id` — `NOT NULL`. Препараты — Этап 3.
2. `Invoice.invoice_number` — отдельное поле, сквозной по клинике, формат
   `2026-000123`, без дыр. Не по кассиру.
3. Одна открытая смена на кассира: `UNIQUE(cashier_employee_id) WHERE
   status='open'` (частичный индекс). Несколько ресепшенов — несколько
   параллельных смен.
4. Только последовательные отдельные `Payment`. Смешанный платёж одной
   записью не делаем.
5. accountant — ноль прав до Этапа 4 (включая сам прейскурант — см. решение
   A в §6). Отчёты Этапа 2 — reception (своя смена), head_doctor (любая).
6. Скидка — жёсткий блок `draft → unpaid`, поля `discount_approved_by_id`/
   `discount_approved_at` на `Invoice`, отдельного статуса
   `pending_discount_approval` нет. Возврат — через `RefundRequest`
   (`invoice_id, payment_id, amount, reason, requested_by_id, status:
   pending|approved|rejected`); неодобренного возврата как `Payment` в БД
   не существует.
7. Порог скидки — `DEFAULT_DISCOUNT_THRESHOLD_PERCENT=10` в `.env`. Таблицы
   `Settings` в Этапе 2 нет — она появится в Этапе 6.
8. Счёт — только вручную. Автосоздание после приёма — кандидат в Этап 6.
9. KZT, тиыны, `BigInteger`, без мультивалютности.

Правила прежние: `BigInteger`-тиыны без `float` нигде; `Payment` append-only
(маршрута `PATCH`/`DELETE` физически нет); цена/название заморожены в
позиции; итоги считает сервер; каждая денежная мутация — в `AuditLog`
(`record_audit()`, Этап 0 коммит 8); счёт+позиции — атомарно, в транзакции;
default-deny; миграции аддитивные с рабочим downgrade; каждый коммит
оставляет проект запускаемым.

## 5. Финализированная модель данных

Дополнения к модели из §1 по итогам решений:

- `Invoice` +`invoice_number` (str, unique, `YYYY-NNNNNN`),
  +`discount_approved_by_id` (FK Employee, nullable),
  +`discount_approved_at` (DateTime, nullable).
- Новая `InvoiceNumberCounter` (`year` PK, `last_number`) — генерация номера
  через `INSERT ... ON CONFLICT(year) DO UPDATE SET last_number =
  last_number + 1 RETURNING last_number` **в той же транзакции**, что и
  вставка `Invoice`. Это гарантирует «без дыр» даже при откате: если
  создание счёта не закоммитилось, откатится и инкремент счётчика — номер
  не будет «сожжён» впустую. Обычная Postgres `SEQUENCE` для этого не
  подходит (она не откатывается вместе с транзакцией).
- `CashShift.cashier_employee_id` — частичный уникальный индекс
  `WHERE status='open'` (решение 3).
- Новая `RefundRequest` (решение 6): `id, invoice_id, payment_id, amount,
  reason, requested_by_id, status (pending|approved|rejected), created_at,
  decided_by_id (nullable), decided_at (nullable)`. При `approved` —
  создаётся `Payment(amount=-request.amount, reversal_of_payment_id=
  request.payment_id, approved_by_id=decided_by_id)`.
- `Payment` — маршрутов `PATCH`/`DELETE` не существует физически (не
  «запрещено ролью», а отсутствует как маршрут — append-only в буквальном
  смысле).

## 6. Решения, принятые самостоятельно (нужно ваше «ок» или правка)

Как и на Этапе 1 (§6.1 там) — несколько механических деталей ваши ответы не
покрывали напрямую:

- **A. Прейскурант (`Service`) тоже вне доступа accountant.** Решение 5
  говорит про «счета/платежи/отчёты», прейскурант явно не упомянут. Трактую
  по духу решения (accountant = «ноль прав до Этапа 4» целиком, не по
  отдельным сущностям) — `GET /api/services` доступен reception, doctor,
  nurse, head_doctor, но не accountant. Если нужно иначе — поправьте.
- **B. Генерация `invoice_number`** — таблица-счётчик с атомарным
  `UPDATE...RETURNING` внутри транзакции создания счёта (детали в §5). Это
  чисто техническое решение «как обеспечить „без дыр"», не бизнес-вопрос,
  но фиксирую явно, т.к. это несёт риск (гонки при параллельном создании
  счетов — `ON CONFLICT DO UPDATE` его снимает).
- **C. Подтверждение скидки — отдельный эндпоинт, не совмещённый с
  выставлением.** Ресепшен вызывает «issue» → 403 если скидка выше порога
  и не одобрена → head_doctor вызывает отдельный `POST
  /invoices/{id}/approve-discount` → ресепшен (или head_doctor) повторяет
  «issue». Альтернатива — head_doctor одобряет и выставляет одним вызовом;
  выбрал двухшаговый вариант, чтобы «issue» всегда означало одно и то же
  независимо от роли вызывающего.
- **D. Отмена счёта (`cancelled`) — только из `draft`/`unpaid`.** Счёт с
  хоть одной оплатой (`partial`/`paid`) через `cancel` не отменяется —
  только через `RefundRequest`. Не было сказано явно, но иначе деньги
  «исчезают» без следа в `Payment`.
- **E. Статус счёта после возврата — не отдельная ветка, а пересчёт.**
  После любого одобренного возврата: `net_paid = Σ Payment.amount
  (включая отрицательные)`; `net_paid <= 0` → `refunded`; `0 < net_paid <
  total` → `partial`; `net_paid >= total` → `paid`. Отдельного статуса
  «частично возвращён» в вашем списке статусов нет — трактую как то же
  самое состояние, что и `partial`.
- **F. Частичный возврат одного платежа разрешён** — `RefundRequest.amount`
  может быть меньше суммы исходного `Payment` (не только «вернуть всё
  целиком»), с проверкой, что сумма уже одобренных возвратов по этому
  платежу плюс новый запрос не превышает исходную сумму.
- **G. Овердрафт запрещён.** `Payment`, который увеличил бы сумму оплат
  сверх `Invoice.total`, отклоняется 409 — не было сказано явно, но иначе
  счёт может стать «переплаченным» без механизма это показать.
- **H. Владение сменой у `CashShift`, как у `Appointment` в Этапе 1.**
  Закрыть/посмотреть отчёт своей смены — reception; любой смены —
  head_doctor. Route-level guard — объединение ролей (решение B, §6.1
  Этапа 1), ветвление по владению — в хендлере.

## 7. Затронутые файлы и последовательность коммитов

14 коммитов (1–14), backend вперёд, тесты — рядом с каждым бэкенд-коммитом
(как в Этапе 1), фронтенд — поверх готового API. Каждый коммит: своя
проверка (миграция вверх/вниз/вверх, pytest, live smoke), краткий отчёт.

1. **Backend: `Service`.** Модель + аддитивная миграция (новая таблица,
   новый enum `service_category`) + `GET /api/services` (читают все, кроме
   accountant/admin — решение A) + `POST/PATCH /api/services/{id}` (только
   head_doctor, `PATCH` включает `is_active`, `DELETE`-маршрута нет).
   *Файлы:* `app/models/service.py`, новая миграция, `app/schemas/service.py`,
   `app/routers/services.py`, `tests/test_services.py`.
2. **Backend: `CashShift` (без отчёта).** Модель + миграция (частичный
   уникальный индекс) + `POST /api/cash-shifts` (открыть), `POST
   /api/cash-shifts/{id}/close`, `GET /api/cash-shifts/current` (своя
   открытая смена). *Файлы:* `app/models/cash_shift.py`, миграция,
   `app/routers/cash_shifts.py`, `tests/test_cash_shifts.py`.
3. **Backend: `Invoice`/`InvoiceItem`.** Модели + миграция (+
   `invoice_number_counters`) + `POST /api/invoices` (draft, с позициями),
   `PATCH /api/invoices/{id}/items`, `POST /api/invoices/{id}/issue`
   (пересчёт, блок по скидке), `POST
   /api/invoices/{id}/approve-discount` (head_doctor), `POST
   /api/invoices/{id}/cancel`. *Файлы:* `app/models/invoice.py`,

5. **Backend: отчёты.** `GET /api/cash-shifts/{id}/report` (своя —

6. **Backend: `RefundRequest`.** Модель + миграция + `POST

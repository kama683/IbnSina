## 1. Что уже работает для reception без изменений

Роль `reception` входит в `_ANY_STAFF` (patients.py, search.py) и
`_VIEW_SCHEDULE` (appointments.py) с Этапа 0 — то есть просмотр и часть
операций уже доступны:

| Возможность | Статус | Где |
|---|---|---|
| Регистрация нового пациента | ✅ Полностью работает | `POST /api/patients` (`_ANY_STAFF`) + модалка «Добавить пациента» в `PatientsToolbar.tsx` |
| Поиск пациента по ФИО/ИИН | ✅ Работает | `GET /api/search`, `GET /api/patients?search=` |
| Просмотр списка приёмов/недели/сегодня | ✅ Работает | `GET /api/appointments*` (`_VIEW_SCHEDULE`) |
| Просмотр живой очереди | ✅ Работает | `GET /api/appointments/queue` |
| Общая навигация/дашборд | ✅ Работает | `(doctors)/layout.tsx` уже role-agnostic с коммита 9 (`getCurrentEmployee()`, не `getCurrentDoctor()`) |

Это меньше половины «регистратуры» из типичного клинического workflow, но
подтверждает, что RBAC-фундамент Этапа 0 достаточен — Этап 1 не требует
новых ролей/эндпоинтов-заглушек, только достройку конкретных операций.

## 2. Конкретные баги/дыры, найденные в текущем коде

Это не гипотезы — сценарии воспроизводятся при логине под reception уже сейчас.

### 2.1 Модалка «Записать пациента» не работает для reception

`front/components/appointments/AppointmentsToolbar.tsx:57-63` — селектор
врача **задизейблен** и всегда показывает `doctorName`, который приходит из
`(doctors)/appointments/page.tsx:76` как `employee.shortName` — то есть
**имя самого залогиненного сотрудника**. Для reception это будет её
собственное имя, не врач.

`back/app/schemas/appointment.py::AppointmentCreateIn` — поля
`patientId/date/time/complaint`, **нет поля выбора врача вообще**.
`back/app/routers/appointments.py::create_appointment` жёстко пишет
`employee_id = <вызывающий сотрудник>` (см. комментарий у `_CREATE_APPOINTMENT`
в коде — reception сознательно исключён из `POST /appointments` в Этапе 0
именно по этой причине).

Итог: reception открывает модалку, видит своё же имя в поле «врач», жмёт
«Записать» → бэкенд ответит 403 (роль не входит в `_CREATE_APPOINTMENT`).
Кнопка сейчас никак не скрыта под ролью — воспроизводится в браузере.

### 2.2 Кнопки «Начать»/«Завершить» на «Живой очереди» не по правам

`front/components/queue/QueueContent.tsx:111-141` — кнопки статуса
(`scheduled → in_progress`, `in_progress → completed`) рендерятся **без
проверки роли**, доступны любому, кто видит очередь — то есть reception и
nurse тоже (`VIEW_SCHEDULE_ROLES` включает обе).

`back/app/routers/appointments.py` — `PATCH /appointments/{id}` защищён
`_MANAGE_EXAMINATION = require_roles(doctor, head_doctor)`. Reception и nurse
получат 403 при клике.

Это зеркало 2.1 — фронт «обещает» действие, бэкенд его блокирует. Требует
решения: либо `RoleGate` на кнопках (быстрый фикс), либо осознанное
расширение `_MANAGE_EXAMINATION` под чек-ин (если nurse/reception должны
физически отмечать приход пациента — вопрос §5.2).

### 2.3 Отмена/перенос приёма — нет вообще

`AppointmentStatus.cancelled` существует в enum с самого начала, но **нигде
не выставляется** — ни одной кнопки/формы «отменить» или «перенести» нет ни
в одном компоненте фронта. Для регистратуры это стандартный сценарий
(пациент звонит и просит отменить/перенести), сейчас нереализуемо в принципе,
не только по правам.

## 3. Что осознанно отложено с Этапа 0 (напоминание из PHASE0_ANALYSIS.md §8)

Записано в решении по вопросу 8: `Appointment.created_by_id`, `service_id`,
`cancelled_*` **не добавлялись** в Этапе 0, отложены на «Этап 1/2». Сейчас
нужно решить, какие из них реально нужны Этапу 1, а какие — позже (см. §5).

но не используется ни одним эндпоинтом — задел явно под Этап 1 (вероятно,
для будущего self-service редактирования, не обязательно под reception
конкретно).

## 5. Открытые вопросы

1. **Выбор врача в форме записи.** Список — все врачи клиники без фильтра,
   или по умолчанию врач участка пациента (`DoctorProfile.area` ==
   `Patient.area`) с возможностью выбрать другого? Нужен ли новый эндпоинт
   `GET /api/employees?role=doctor` (список) — и кому он доступен (только
   reception, или всем `_VIEW_SCHEDULE`-ролям)?

2. **Кто может делать чек-ин на «Живой очереди».** Сейчас кнопки
   «Начать»/«Завершить» технически доступны reception и nurse на фронте, но
   бэкенд их блокирует (`_MANAGE_EXAMINATION` = только doctor/head_doctor).
   Оставляем как есть и просто прячем кнопки (`RoleGate`) для не-клиницистов,
   или расширяем право переводить `scheduled → in_progress` (не
   `→ completed`) на reception/nurse — как в реальной регистратуре, где
   администратор отмечает «пациент пришёл»?

3. **Отмена/перенос приёма.** Нужны ли отдельные поля
   `cancelled_at`/`cancelled_by_id`/`cancellation_reason` на `Appointment`,
   или достаточно `status=cancelled` + запись в `AuditLog` (уже подключён с
   коммита 8)? Кто может отменять — только reception, или ещё и сам
   назначенный врач? «Перенести» — это отдельная операция (правка
   date/time существующей записи) или отмена старой + создание новой?

4. **`Appointment.created_by_id`.** Нужно ли явное поле «кем создана запись»
   на самой сущности (для отображения в UI, например бейдж «записал(а):
   Иванова А.К.»), или отметки в `AuditLog` достаточно и поле не нужно?

5. **`Appointment.service_id`.** Похоже на связку с прайсом/услугами — а
   таблицы услуг в системе ещё нет вообще (это скорее Этап 2, финансы).
   Подтвердите: `service_id` **вне рамок** Этапа 1, добавляется позже вместе
   с модулем услуг/биллинга?

6. **Проверка занятости врача при записи.** Сейчас конфликт-чек — точное
   совпадение `(employee_id, date, time)`. Нужно ли на Этапе 1 сверяться с
   рабочим графиком врача (`Schedule` — есть по дням недели с start/end), не
   давая записать вне рабочих часов, или пока оставить только
   slot-collision без проверки графика?

7. **Редактирование карточки пациента.** Сейчас есть только `POST
   /api/patients` (создание). Нужен ли `PATCH /api/patients/{id}` в рамках
   Этапа 1 (например, если ИИН/телефон внесли с опечаткой), или это тоже
   не в рамках и остаётся для другого этапа?

8. **Отдельная секция фронта под reception.** Оставляем один общий route
   group `(doctors)` (сейчас уже role-agnostic layout, просто донастраиваем
   конкретные компоненты под роль), или заводим отдельный `(reception)` с
   собственной стартовой страницей/дашбордом (например, сразу видна форма
   быстрой записи + живая очередь, без «Профиля врача» и т.п.)?

Жду ответы — как и с Этапом 0, реализация начинается только после того, как
эти вопросы закрыты.

## 6. Решения (получены 2026-08-08) и уточнённый план

Источник истины по Этапу 1 — эти решения, не файл плана (он всё ещё чинится
отдельно; реконструкция по коду признана верной пользователем).

1. `GET /api/employees?role=doctor` — только активные, минимум полей (`id`,
   `shortName`, `area`, `specialty`), без кадровой PII. Доступ: reception,
   doctor, head_doctor. В форме записи по умолчанию — врач участка пациента
   (`DoctorProfile.area == Patient.area`), reception может выбрать любого.
2. Права на чек-ин очереди не расширяем. `RoleGate` прячет
   «Начать»/«Завершить» у всех, кроме doctor/head_doctor.
   `_MANAGE_EXAMINATION` без изменений. Статуса «пришёл» в этом этапе нет.
3. `Appointment` +`cancelled_at`, `cancelled_by_id`, `cancellation_reason`
   (аддитивная миграция). Отмена: reception, head_doctor — любой приём;
   назначенный врач — только свой. «Перенести» = `PATCH` даты/времени той же
   записи + повторный конфликт-чек, не отмена+создание.
4. `Appointment` +`created_by_id`, ставится = вызывающий сотрудник при
   создании, nullable, старые записи — `NULL` (бэкфилл не нужен, поля не
   существовало). Нужен для бейджа «записал(а): …».
5. `service_id` — вне Этапа 1, в Этап 2 (модуль услуг).
6. Слоты записи — из `Schedule` выбранного врача (день недели → `day_id`,
   `enabled`/`start`/`end`); запись вне рабочих часов или в выключенный день
   — жёсткий 400. Конфликт-чек — как раньше, но по выбранному `employee_id`.
7. `PATCH /api/patients/{id}` — только демографические поля, `require_roles
   (reception, head_doctor)`, уникальность ИИН (409, исключая себя). `Patient`
   +`updated_at`, `updated_by_id`.
8. Один route group `(doctors)`, layout не форкаем. Reception получает свою
   стартовую страницу (быстрая запись + очередь по всем врачам, без
   врачебных виджетов) и меню без врачебных пунктов. Переименование группы —
   не сейчас.
9. Автокомплит пациента в форме записи вместо `<select>`.
10. Flow «поиск по ИИН»: найден → открыть карточку; не найден → форма
    создания с предзаполненным ИИН.

Правила прежние: default-deny (каждый новый маршрут — явная роль, иначе
красный тест матрицы), проверка прав всегда на бэке, миграции аддитивные с
рабочим downgrade, каждый коммит оставляет проект запускаемым, ничего из
Этапов 2+ не заводим.

### 6.1 Решения, принятые самостоятельно (нужно ваше «ок» или правка)

Формулировки в §5/6 не покрывали три механических детали — принял разумные
умолчания, но это решения, которые стоит подтвердить явно, а не молча
принять как должное:

- **A. Кого включает `role=doctor`.** `head_doctor` тоже имеет
  `doctor_profile` (это установлено ещё в сиде Этапа 0) и в реальной клинике
  ведёт приём наравне с doctor. Предлагаю фильтровать не по строгому
  `Employee.role == 'doctor'`, а по «есть `doctor_profile` и `status=active`»
  — тогда head_doctor тоже попадает в список для записи. Параметр в URL
  остаётся `role=doctor` (это про смысл эндпоинта — «покажи мне
  клиницистов», а не про точное сравнение с колонкой).
- **B. Права на `PATCH /appointments/{id}` перестают быть одной ролью.**
  Сейчас это единая зависимость `_MANAGE_EXAMINATION` (doctor/head_doctor) на
  весь эндпоинт. С отменой/переносом, доступными ещё и reception (безусловно)
  и «своему» врачу (только свой приём), одной ролевой зависимостью уже не
  обойтись — нужна проверка в теле хендлера: какие поля пришли (осмотр vs
  отмена/перенос) и чей это приём. Осмотр/диагноз/назначения остаются
  doctor/head_doctor-only; отмену/перенос разрешаю по правилу из решения 3.
- **C. Эндпоинта «график вот этого врача» не существует.** Есть только
  `/employees/me/profile` (только свой). Чтобы фронт мог посчитать доступные
  слоты для ВЫБРАННОГО врача, нужен либо новый эндпоинт с его графиком, либо
  (предпочтительнее — не дублировать бизнес-логику валидации на клиенте)
  новый `GET /api/appointments/available-slots?employeeId=&date=`,
  считающий слоты на бэке (та же функция переиспользуется для 400-валидации
  при создании/переносе). Иду по второму варианту.
- **D. Календарная сетка `TIME_SLOTS` (08:00–13:00) в `calendar-utils.ts`.**
  Читаю решение 6 как «слоты в форме записи», не как «сетка отображения
  недельного календаря» (это разные вещи — календарь просто рисует строки
  для уже существующих приёмов всех врачей). Сетку календаря не трогаю в
  этом этапе.

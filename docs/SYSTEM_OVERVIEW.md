# IbnSina — документация системы

Информационная система городской поликлиники: рабочее место врача для ведения
приёмов, живой очереди, карточек пациентов и осмотров. Ниже — полное описание
того, что система делает, как устроена бизнес-логика, какие роли есть и что
пока не реализовано.

## 1. Общее описание

**Что это.** Веб-приложение для врача поликлиники (терапевт/эндокринолог —
в демо-данных врач-эндокринолог) — цифровое рабочее место на смену: кто
записан на сегодня, кто сейчас на приёме, карточка каждого пациента с полной
историей, оформление осмотра с диагнозом и назначениями.

**Для кого.** Один врач = одна учётная запись = один кабинет. Система ведёт
пациентов своего участка, но физически видит всех пациентов в БД (участковая
принадлежность — это поле фильтрации, а не жёсткая изоляция данных).

**Технологии.**

| Слой | Технология |
|---|---|
| Frontend | Next.js 16 (App Router, React Server Components), TypeScript, Tailwind CSS |
| Backend | FastAPI, SQLAlchemy ORM, Pydantic-схемы |
| БД | PostgreSQL, миграции через Alembic |
| Авторизация | JWT (HS256), пароли — bcrypt |

**Как соединены части.** Frontend — отдельное Next.js-приложение (порт 3000),
backend — отдельный FastAPI-процесс (порт 8000). Клиент обращается к API
напрямую по HTTP (`NEXT_PUBLIC_API_URL`), в том числе из серверных компонентов
(RSC) — то есть большая часть страниц рендерится на сервере Next.js, который
сам делает fetch к FastAPI при каждом заходе на страницу.

## 2. Роли и авторизация

**Роли (заложены в модели, но UI различий по ролям нет):**

- `doctor` — врач. Единственная роль, для которой сегодня есть реальный
  функционал (профиль врача, приёмы, осмотры).
- `admin`, `nurse` — определены в перечислении `UserRole`, но нигде в бизнес-
  логике/UI не используются. Задел на будущее.

**Как устроен вход.**

1. Пользователь вводит email и пароль на `/login`.
2. Backend (`POST /api/auth/login`) сверяет bcrypt-хеш пароля и выпускает JWT
   (срок жизни — 7 дней по умолчанию, `ACCESS_TOKEN_EXPIRE_MINUTES`).
3. Токен кладётся в cookie `auth_token` на стороне браузера и используется как
   `Authorization: Bearer <token>` для всех запросов к API — и с сервера
   (Server Components читают cookie через `next/headers`), и из браузера
   (клиентские компоненты читают `document.cookie`).
4. Прокси-уровень Next.js (`proxy.ts`, аналог `middleware.ts`) редиректит на
   `/login` любой запрос без cookie; если cookie есть — не пускает обратно на
   `/login`.
5. Любой ответ backend со статусом 401 (истёкший/невалидный токен) на клиенте
   чистит cookie и уводит на `/login`.
6. Все API-роуты, кроме `/api/auth/login`, требуют валидный токен
   (`Depends(get_current_user)`, подключено на уровне `main.py` ко всем
   роутерам разом).

**Связь пользователь ↔ врач.** Таблица `users` хранит логин/пароль/роль и
ссылку `doctor_id` на запись в `doctors`. Профильные данные (ФИО, стаж,
кабинет и т.д.) живут в `doctors`, а не в `users` — `users` только про доступ.
Каждый защищённый эндпоинт резолвит «текущего врача» через
`current_user.doctor_id`, а не «первого врача в базе» — то есть система
технически готова к нескольким врачам с раздельными данными, но UI создания
новых пользователей/врачей отсутствует (заводить руками через `seed.py` или
БД).

## 3. Модули системы

### 3.1 Дашборд (`/`)

Главная страница врача после входа. Собирает четыре виджета:

- **Текущий приём** — если у врача есть приём в статусе «на приёме» на
  сегодня, показывается карточка с пациентом, жалобой и кнопкой «Открыть»
  (ведёт на осмотр). Если сейчас никто не принимается — блок не отображается.
- **Приёмы на сегодня** — таблица всех приёмов на текущую дату (любой статус),
  со ссылкой «Все приёмы» на полный список.
- **Ближайшие** — до 3 приёмов со статусом «Записан» из сегодняшнего списка.
- **Статистика за неделю** — агрегаты по текущей неделе (пн–сб): всего
  приёмов, завершённых, отменённых, новых пациентов, диспансерных, среднее
  время приёма.

### 3.2 Приёмы (`/appointments`)

Два режима отображения, переключаются кнопкой в тулбаре:

- **Список** — приёмы за выбранную дату (пикер даты), в виде таблицы.
- **Календарь** — сетка на неделю (пн–сб), с шагом 30 минут в диапазоне
  08:00–13:00 (`TIME_SLOTS`), плюс навигация «неделя назад/вперёд» через
  query-параметр `?week=N`. Карточки приёма подсвечиваются цветом по статусу.

**Запись пациента на приём** — модальное окно: выбор пациента из списка (без
поиска — простой `<select>`), дата, время, жалоба. При сохранении backend
проверяет, что у врача на это время ещё нет приёма (`409`, если слот занят).
Врач в форме зафиксирован (поле неактивно) — записать можно только «на себя»,
мультидокторской записи в UI нет.

### 3.3 Живая очередь (`/queue`)

Список пациентов, записанных **на сегодня** и находящихся в статусе
«Записан» или «На приёме» (завершённые/отменённые в очередь не попадают).
Наверху — плашка с текущим пациентом на приёме (если есть).

Действия прямо из очереди:

- «Начать» (для статуса «Записан») → переводит приём в «На приёме».
- «Осмотр» и «Завершить» (для статуса «На приёме») → «Осмотр» ведёт на форму
  осмотра, «Завершить» закрывает приём без захода в осмотр.

### 3.4 Пациенты (`/patients`)

Список всех пациентов в БД (не только участка врача) с пагинацией по 8 на
страницу. Поиск — по ФИО или ИИН (без учёта пробелов в ИИН), фильтр — по
участку (список участков строится из фактических данных, не хардкодится).
Поиск/фильтр/страница синхронизированы с URL (`?search=&area=&page=`) — можно
поделиться ссылкой на конкретную выборку.

**Создание пациента** — модальная форма: ФИО, ИИН, дата рождения, пол,
телефон, адрес, участок (по умолчанию — участок врача), группа крови,
чекбокс «диспансерный учёт». ИИН должен быть уникален — иначе `409`.

В таблице у каждого пациента видно: ИИН, дату рождения + возраст, участок,
дату последнего приёма, цветные теги диспансерных диагнозов.

### 3.5 Карточка пациента (`/patients/[id]`)

Шапка с общей сводкой + 4 вкладки:

1. **Основное** — личные данные (ФИО, дата рождения, пол, ИИН, телефон,
   адрес, участок); если пациент госпитализирован — отдельный блок
   «Стационарное лечение» (отделение, палата, койка, дата поступления,
   лечащий врач, диагноз при поступлении); диспансерные диагнозы (цветные
   теги); аллергии (красный блок-предупреждение); группа крови; хронические
   заболевания.
2. **История болезни** — список всех приёмов пациента (за всё время, у любого
   врача), с датой, статусом, жалобой и диагнозом.
3. **Паспорт здоровья** — показатели здоровья (рост, вес, ИМТ, АД, ЧСС,
   сатурация, глюкоза, холестерин и т.п.) с датой измерения и опциональной
   пометкой (например, «избыточный» у ИМТ).
4. **Прививки** — история вакцинации: название, препарат+серия (в БД хранится
   одной строкой через «, серия », на фронт приходит уже разобранным), дата,
   примечания.

Карточка пациента **только для чтения** — редактирование основных данных
пациента через UI не реализовано (можно только создать нового).

### 3.6 Осмотр пациента (`/patients/[id]/examination`)

Форма ведения текущего приёма. Открывается для пациента, у которого есть
**активный приём** — backend ищет сначала приём в статусе «На приёме» у этого
пациента, а если такого нет — приём на сегодня в статусе «Записан» (в этом
порядке). Если ни того, ни другого нет — 404 «активный приём не найден».

Поля:

- **Жалобы** — свободный текст.
- **Объективный статус** — свободный текст с плейсхолдером-подсказкой
  (АД/ЧСС/ЧДД/температура/состояние).
- **Диагноз (МКБ-10)** — поиск по справочнику МКБ-10 (локальный JSON-файл на
  backend, `icd10_common.json`) с debounce 250 мс от 2 символов, до 10
  совпадений по коду или названию; выбранные диагнозы — теги с возможностью
  удаления. Хранится только один основной диагноз (первый выбранный код +
  название пишутся в `diagnosis_code`/`diagnosis_name` приёма) — если
  добавить несколько, в БД сохранится только первый.
- **Назначения** — динамический список: препарат, дозировка, длительность.
  Минимум одна пустая строка всегда показывается; пустые строки при
  сохранении не пишутся в БД.

Две кнопки сохранения:

- **«Сохранить черновик»** → PATCH с `status = in_progress` (приём остаётся
  открытым, но данные фиксируются).
- **«Завершить приём»** → PATCH с `status = completed`. При завершении, если
  `duration_minutes` ещё не проставлена, backend подставляет **18 минут по
  умолчанию**.

При переводе приёма в «На приёме» backend автоматически переводит обратно в
«Записан» все другие приёмы этого врача на эту дату, которые были «На
приёме» — то есть **у врача может быть только один активный приём
одновременно**.

### 3.7 Профиль врача (`/profile`)

Просмотр и редактирование собственного профиля:

- **Сводка** — ФИО, инициалы, роль, участок, бейджи (категория —
  «Высшая категория» и т.п., плюс статичный бейдж «КМО активен»).
- **Контакты** — телефон, email (редактируемые), место работы (только
  чтение).
- **Показатели** (только чтение, считаются на лету при каждом запросе):
  число пациентов на участке врача, число приёмов врача с начала текущего
  месяца, число пациентов участка на диспансерном учёте, стаж (лет).
- **Профессиональная информация** — специальность, категория, номер/срок
  действия лицензии, номер/срок действия сертификата (только чтение), «О себе»
  (редактируемое).
- **График работы** — по дням недели: включён/выключен + время начала/конца;
  переключается тумблером, время — обычные `<input type="time">`.
- **Образование** — список записей (год, учреждение/курс, описание), только
  чтение через UI.

Сохранение — одна кнопка «Сохранить изменения», уходит одним PATCH-запросом
(about, phone, email, schedule целиком). «Отменить» — сбрасывает несохранённые
локальные правки к последним данным с сервера.

### 3.8 Глобальный поиск (шапка, доступен с любой страницы)

Поле поиска в хедере: debounce 300 мс, от 2 символов, ищет параллельно среди
пациентов (по ФИО/короткому имени/ИИН, до 5) и приёмов (по имени пациента или
жалобе, до 5). Результат — выпадающий список со ссылками на карточку
пациента.

### 3.9 Настройки (`/settings`)

**Заглушка.** Раздел явно помечен «в разработке» — блоки «Уведомления» и
«Оформление» показывают текст-обещание, реальных настроек (push/email,
тёмная тема) нет. Единственный работающий контент — статичная информация
«О системе» (версия, стек).

## 4. Ключевые бизнес-правила

Эта секция — то, что не видно из UI напрямую, но определяет поведение
системы.

- **Статусы приёма и переходы.** `scheduled → in_progress → completed`,
  либо `scheduled → cancelled`. Явного запрета на «откат» статуса в API нет
  (PATCH принимает любой статус), но UI предлагает только переходы вперёд.
- **Один активный приём на врача.** При переводе приёма в `in_progress` все
  прочие приёмы этого врача за тот же день, ранее бывшие `in_progress`,
  автоматически переводятся обратно в `scheduled`.
- **Длительность приёма по умолчанию.** При завершении приёма
  (`status = completed`), если `duration_minutes` ещё не задана — подставляется
  **18 минут**. Это число участвует в расчёте «среднее время приёма» в
  недельной статистике (считается только по уже завершённым приёмам с
  заданной длительностью).
- **Конфликт записи.** Нельзя создать два приёма одному врачу на одну и ту же
  дату+время — `409 Conflict`.
- **Поиск активного приёма для осмотра.** Сначала ищется приём `in_progress`
  у пациента (в любой день), и только если такого нет — приём `scheduled` на
  **сегодня**. Если пациент записан на будущую дату — открыть «Осмотр» для
  него нельзя, пока приём не переведён в работу.
- **Уникальность ИИН.** Пациент с уже существующим ИИН не создаётся повторно
  — `409 Conflict`.
- **Короткое ФИО.** Формируется backend-ом автоматически из полного имени:
  «Фамилия И.О.» (для 3 слов), «Фамилия И.» (для 2 слов), иначе — как есть.
- **Возраст.** Считается на лету от `birth_date`, с грамматически правильным
  склонением «год/года/лет» по числу (стандартные русские правила: 11–14 —
  всегда «лет», иначе по последней цифре).
- **Стационар vs амбулатория.** У пациента может быть максимум одна активная
  запись о госпитализации (`hospitalizations`, в сиде — «текущая», без явного
  флага «выписан»). Если она есть — `careType = "inpatient"` и в карточке
  показывается блок «Стационарное лечение»; если нет — `"ambulatory"`.
  Отделение (`department`) в госпитализации — просто текстовое поле, отдельной
  сущности «Отделение» в системе больше нет (была — убрана как неиспользуемый
  код).
- **Диспансерный учёт.** Булево поле на пациенте (`dispensary`), плюс
  отдельная сущность «диспансерные диагнозы» (`diseases`, с цветным тегом —
  6 вариантов цвета) — это разные вещи: пациент может стоять на диспансерном
  учёте вообще без привязанных диагнозов-тегов, и наоборот.
- **Участок (`area`).** Свободная строка и на враче, и на пациенте — единый
  список участков в фильтре собирается динамически (`DISTINCT` по пациентам),
  не хардкодится. «Мои пациенты» как отдельного фильтра нет — список
  пациентов не ограничен участком врача, участок используется только для
  фильтрации/отображения и для расчёта метрик в профиле врача.
- **Диагноз приёма.** Хранится как пара `diagnosis_code` + `diagnosis_name`
  (не список) — несмотря на то что форма осмотра позволяет добавить
  несколько кодов, в БД попадает только первый.
- **Вакцинация: препарат+серия.** В БД это одно строковое поле `dose`
  ("Гриппол Плюс, серия ГФ-2025-01"), backend разбирает его по разделителю
  ", серия " в два поля для фронта (`drug`, `series`).

## 5. Модель данных

| Сущность | Ключевые поля | Связи |
|---|---|---|
| `User` | email (unique), full_name, password_hash, role (doctor/admin/nurse) | 1:1 → `Doctor` (через `doctor_id`) |
| `Doctor` | full_name, short_name, initials, role (специальность), area, title, office, phone, email, workplace, specialty, qualification_category, license_*, certificate_*, about, experience_years | 1:N → `Appointment`, `Hospitalization`, `Schedule`, `DoctorEducation`; 1:1 ← `User` |
| `Schedule` | day_id, label, enabled, start, end | N:1 → `Doctor` |
| `DoctorEducation` | year, title, description | N:1 → `Doctor` |
| `Patient` | iin (unique), full_name, short_name, birth_date, gender, phone, address, area, blood_type, dispensary | 1:N → `Appointment`, `PatientDisease`, `PatientAllergy`, `Vaccination`, `Hospitalization`, `HealthMetric` |
| `Appointment` | date, time, complaint, status, diagnosis_code, diagnosis_name, objective_status, duration_minutes | N:1 → `Patient`, `Doctor`; 1:N → `Prescription` |
| `Prescription` | medication, dosage, frequency | N:1 → `Appointment` |
| `PatientDisease` | label, variant (цвет тега) | N:1 → `Patient` |
| `PatientAllergy` | name | N:1 → `Patient` |
| `Vaccination` | name, date, dose (препарат+серия одной строкой), notes | N:1 → `Patient` |
| `Hospitalization` | department, ward, bed, admitted_at, primary_diagnosis | N:1 → `Patient`, `Doctor` |
| `HealthMetric` | label, value, date, note | N:1 → `Patient` |

## 6. Справочник API

Базовый префикс — `/api`. Всё, кроме `/auth/login`, требует
`Authorization: Bearer <token>`.

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/auth/login` | Вход, выдаёт JWT |
| GET | `/auth/me` | Текущий пользователь |
| GET | `/doctors/me` | Краткие данные врача (для шапки/сайдбара) |
| GET | `/doctors/me/profile` | Полный профиль врача |
| PATCH | `/doctors/me` | Обновить профиль (about/phone/email/schedule) |
| GET | `/appointments?from&to` | Приёмы за диапазон дат |
| GET | `/appointments/week` | Приёмы текущей недели |
| GET | `/appointments/stats/week` | Статистика за неделю |
| GET | `/appointments/queue` | Живая очередь на сегодня |
| GET | `/appointments/today` | Все приёмы на сегодня |
| GET | `/appointments/current` | Текущий приём (in_progress) |
| POST | `/appointments` | Создать запись на приём |
| PATCH | `/appointments/{id}` | Обновить приём (статус/осмотр/диагноз/назначения) |
| GET | `/patients?page&limit&search&area` | Список пациентов с пагинацией |
| POST | `/patients` | Создать пациента |
| GET | `/patients/{id}` | Карточка пациента |
| GET | `/patients/{id}/history` | История приёмов пациента |
| GET | `/patients/{id}/health-metrics` | Паспорт здоровья |
| GET | `/patients/{id}/vaccinations` | Прививки |
| GET | `/patients/{id}/examination` | Данные для формы осмотра (активный приём) |

## 7. Известные ограничения / что не реализовано

- **Настройки** — заглушка (нет push/email-уведомлений, нет темы).
- **Управление пользователями/врачами** — нет UI для создания новых
  врачей/пользователей или смены пароля; только через `seed.py`/БД напрямую.
- **Роли `admin`/`nurse`** — существуют в модели, но не имеют отдельного UI
  или ограничений доступа (любой залогиненный пользователь видит всё, доступ
  не различается по роли).
- **Редактирование карточки пациента** — данные пациента можно только
  посмотреть и создать нового; изменить существующего (телефон, адрес,
  аллергии и т.д.) через интерфейс нельзя.
- **Многодокторская запись** — форма записи на приём всегда пишет на
  текущего авторизованного врача; выбора другого врача нет.
- **Refresh-токены** — их нет: токен просто живёт 7 дней и всё, механизма
  «тихого» обновления сессии нет (по истечении — редирект на `/login`).
- **Тестов нет** — ни автотестов backend, ни frontend.
